# BotFlow Builder

Конструктор Telegram-воронок с React/Vite админкой, Express API, Telegram WebApp-страницами, мультиботами, Supabase-хранилищем и интеграцией платежей Lava.top.

## Возможности

- создание и редактирование Telegram-воронок;
- подключение нескольких Telegram-ботов;
- премиальные WebApp-страницы как React-компоненты, редактируемые через код;
- учет подписчиков, сообщений и заказов;
- Supabase как обязательное production-хранилище; локальные JSON-файлы только для разработки;
- загрузка изображений и видео, включая обработку video note через `ffmpeg`;
- тестовая оплата через `/mock-checkout` и production-заготовка под Lava.top.

## Что нужно установить

Минимум, чтобы проект заработал у вас на компьютере:

- **Node.js 20 или новее** — [nodejs.org](https://nodejs.org). Проверить: `node --version`.
- **Свой Telegram-бот** — получить токен у [@BotFather](https://t.me/BotFather) командой `/newbot`.

Этого хватит для локального запуска: данные лягут в JSON-файлы в `data/`, оплата
работает в тестовом режиме через `/mock-checkout`.

Дальше — по мере надобности:

- **Supabase** (бесплатного тарифа хватает) — обязателен для боевого режима,
  локально не нужен;
- **ffmpeg** — только для кружочков-видео в Telegram: `brew install ffmpeg`;
- **Lava.top** — для реальных платежей вместо тестовых;
- **Railway** или любой Docker-хостинг — чтобы выложить проект в интернет.

Ключи каждый заводит свои: чужие токены и URL из примеров не подойдут и не нужны.

## Локальный запуск

Требования:

- Node.js 20+;
- `ffmpeg` и `ffprobe`, если нужна обработка Telegram video note;
- Supabase-проект для production-авторизации и хранения данных.

```bash
npm install
npm run dev:local-login
```

Приложение будет доступно на `http://localhost:3000`.

`npm run dev:local-login` — самый простой локальный запуск: он явно включает loopback-only dev bypass и не использует production Supabase или боевых Telegram-ботов. `npm run dev` оставляет защищённый вход включённым и подходит, когда настроены `DEV_SUPABASE_*`.

## Переменные окружения

Скопируйте `.env.example` в `.env` и заполните нужные значения.

Основные переменные:

- `APP_URL` - публичный URL приложения, нужен для Telegram WebApp-ссылок и webhook URL.
- `ADMIN_EMAIL` - email единственного админа; только этот Supabase-пользователь имеет доступ к админским API. Обязателен в production.
- `VITE_ADMIN_EMAIL` - тот же email для проверки на форме входа (опционально, для UX).
- `SUPABASE_URL` - URL Supabase-проекта для серверного хранения.
- `SUPABASE_SERVICE_KEY` - service role key, используется только сервером.
- `VITE_SUPABASE_URL` - URL Supabase-проекта для фронтенд-авторизации.
- `VITE_SUPABASE_ANON_KEY` - anon key для Supabase Auth на фронте.
- `DEEPSEEK_API_KEY` - ключ DeepSeek для ИИ-ассистента воронок. Необязателен: обычно ключ вводится в разделе «Настройки» админки, а переменная нужна как запасной путь для автодеплоя.
- `GEMINI_API_KEY` - ключ AI-провайдера для генерации в редакторе, если используется.
- `XAI_API_KEY`, `GROQ_API_KEY`, `OPENAI_API_KEY` - распознавание голосовых сообщений подписчиков. Провайдеры пробуются в этом порядке, достаточно любого одного (Gemini тоже участвует, если задан). Без ключей бот честно просит написать текстом. Ключ xAI можно ввести и в разделе «Настройки» админки - он перекрывает переменную.
- `VITE_DEFAULT_FUNNEL_ID` - воронка, которая открывается по адресу без параметров: статичная кнопка «Открыть приложение» у BotFather и путь `/sitelab`. Подставляется при сборке фронтенда, поэтому в Docker это ещё и build-arg.
- `LAVA_API_KEY` - API key Lava.top.
- `LAVA_WEBHOOK_SECRET` - secret для webhook с заголовком `x-api-key`.
- `TELEGRAM_BOT_TOKEN` - env-токен для бота, если в `data/settings.json` у бота указан `__ENV_TELEGRAM_BOT_TOKEN__`.

Telegram-боты добавляются через раздел настроек в админке. Для продакшена безопаснее хранить токен в переменных окружения, а в настройках оставлять placeholder `__ENV_TELEGRAM_BOT_TOKEN__`.

## Supabase

1. Создайте Supabase-проект.
2. Выполните SQL из `supabase-schema.sql` в Supabase SQL Editor.
3. Добавьте `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` в `.env` или переменные деплоя.
4. Создайте пользователя через Supabase Auth или форму регистрации.

В production админские API требуют валидный Supabase JWT. Публичными остаются WebApp-страницы, healthcheck, media GET, tracking и payment endpoints.

После обновления проекта повторно выполняйте `supabase-schema.sql`: скрипт идемпотентен,
добавляет недостающие поля и создаёт server-only таблицу `payment_intents`, необходимую
для связи реальных Lava.top-платежей с Telegram-пользователями. В production сервер
не переключается на JSON при ошибке Supabase: запуск завершается, а Railway повторяет его.

## Lava.top

Webhook URL в кабинете Lava.top:

```text
{APP_URL}/api/webhook/lava
```

Тип авторизации: API key. Значение должно совпадать с `LAVA_WEBHOOK_SECRET`; SDK проверяет его через заголовок `x-api-key`.

## Воронка внутри Telegram (Mini App)

У воронки есть переключатель **«Открывать внутри Telegram»** (карточка кнопки
меню в редакторе воронки). Он включает режим Mini App:

- кнопки этапов, напоминаний и «продолжить обучение» открывают страницу нативно
  (`web_app`), а не внешней ссылкой в браузере;
- следующий этап уходит в чат сразу, без паузы: страница закрывается мгновенно,
  и сообщение должно уже лежать в переписке;
- страницы уроков оформляются под интерфейс Telegram.

Выключено - страницы открываются обычной ссылкой, как на сайте.

Раньше этот режим был зашит в коде по идентификатору воронки сразу в нескольких
файлах, поэтому включить его для своей воронки было нельзя. Признак приходит на
страницу с сервера полем `telegramMiniApp`, компоненты читают его из контекста.

Цены пакетов раньше тоже жили в коде и появлялись у двух воронок сами собой.
Теперь офферы берутся только из настроек этапа: сервер не знает ни одного
идентификатора воронки - это проверяется тестом в `server/__tests__/funnelSettings.test.ts`.

## Ограничения масштабирования

Приложение рассчитано на **один инстанс**. В памяти процесса живут:

- активные Telegram-боты (polling или webhook-обработчики);
- таймеры напоминаний (`setTimeout`, восстанавливаются при старте);
- очередь рассылок и планировщик запланированных кампаний.

Если поднять вторую реплику, каждая начнёт независимо отправлять напоминания и
рассылки — подписчики получат дубли. Поэтому в Railway держите `Replicas = 1`
и не включайте autoscaling. При старте сервер проверяет `WEB_CONCURRENCY`,
`NUM_REPLICAS` и `RAILWAY_REPLICA_COUNT` и пишет в лог ошибку, если реплик больше одной.

Что переживает перезапуск:

| Данные | Как восстанавливаются |
| --- | --- |
| Воронки, подписчики, заказы, прогресс | Загружаются из Supabase (локально — из `data/`) |
| Напоминания | `resumePendingReminders()` пересоздаёт таймеры по сохранённым задачам |
| Рассылка в процессе отправки | Прогресс пишется каждые 25 получателей; при старте кампания догружается по слепку аудитории |
| Сообщение с доступом после покупки | Статус доставки сохранён в заказе; неуспешная отправка повторяется после запуска ботов |

Заказы, подписчики, воронки и прогресс загружаются по всем страницам ответа
Supabase. Реестр покупок не обрезается до 1000: старые оплаты продолжают давать
доступ. Полная история и рабочие состояния хранятся в памяти одного инстанса,
поэтому потребление памяти растёт вместе с аудиторией.

Очередь сообщений об оплате проверяется каждые 30 секунд, до 20 заказов за проход.
После ошибки следующая попытка назначается через 1 минуту; задержка постепенно
растёт до часа. Задача создаётся вместе с новым заказом. Старые заказы без статуса
доставки автоматически не рассылаются заново. Если процесс завершился после
успешной отправки в Telegram, но до сохранения её результата, возможен повтор
уведомления; повторной покупки при этом не создаётся.

Лимиты отправки: ~20 сообщений/сек (запас к лимиту Telegram ~30/сек), не более
100 получателей за ручной запуск (подтверждается фразой «ОТПРАВИТЬ N») и не более
1000 — за один запуск запланированной кампании.

## Миграции Supabase

DDL через service-ключ выполнить нельзя — PostgREST даёт доступ только к данным.
Поэтому изменения схемы применяются вручную в **SQL Editor** проекта Supabase:
содержимое `supabase-schema.sql` идемпотентно, его можно прогонять целиком.

Код не требует миграции для запуска. Если колонок ещё нет, сервер один раз пишет
предупреждение в лог и сохраняет профиль подписчика без них — регистрация и
рассылки продолжают работать, а пометки «заблокировал бота» и «ждёт оператора»
живут только в памяти до перезапуска. После применения миграции достаточно
перезапустить сервис.

Исправления аудита от 6 сентября 2026 используют существующие поля `profile`
и снимок товара в `orders.product`; новых SQL-колонок для них не требуется.
При старте сервис сверяет старую резервную строку прогресса `__user_progress__`
с основной таблицей по времени сохранения. После переноса актуальных состояний
резервная строка удаляется. Если перенос не завершился, строка остаётся для
следующей попытки; при отсутствии колонки `profile` требуется применить текущую
схему. Временная ошибка БД теперь возвращается как ошибка сохранения и не
переключает записи в другую таблицу.

Домашние задания восстанавливаются вместе с профилем. Данные, уже затёртые
старой версией, исправление само не восстанавливает — для них нужна резервная
копия. То же относится к локальным заказам, ранее удалённым ограничением истории.

Начисления бонусов привязаны к существующим урокам доступного тарифа. Если
начисленные за урок бонусы уже потрачены и баланса не хватает для полного
возврата, снятие отметки о прохождении не отменяет это начисление. Повторная
отметка не выдаёт бонус второй раз. Ключи начислений хранятся отдельно от
ограниченной истории операций.

## Откуда пришёл подписчик

Telegram передаёт боту метку из диплинка: ссылка вида

```
https://t.me/<бот>?start=ad_vk_01
```

приходит как `/start ad_vk_01`. Метка сохраняется в досье подписчика **один раз** —
это источник, который его привёл, а не последний клик: человек, вернувшийся через
месяц по другой ссылке, остаётся за первым источником.

Метка чистится от посторонних символов и обрезается до 64 знаков: приходит она
из внешнего мира, доверять ей нельзя. Разрешены латиница, цифры, дефис и подчёркивание.

Источник виден в карточке контакта в «Аудитории» и попадает в контекст ассистента,
так что дожим знает, по какому объявлению человек пришёл.

## Вопросы и профиль подписчика

Этап может задать подписчику вопрос с вариантами ответа — кнопки уходят следом за
сообщением этапа. Ответ ложится в профиль под своим ключом (`goal`, `level`, …),
а вариант может увести человека на другой этап, то есть развести воронку на ветки.

Профиль — это досье подписчика: ответы на вопросы и состояние долгого дожима в одной
JSONB-колонке, чтобы каждая новая функция не требовала своей миграции.
Оно видно ассистенту: он опирается на него
и в ответах, и в персонализации напоминаний. Вопросы задаются по одному — следующий
уходит только после ответа на предыдущий.

Идентификаторы вопросов и вариантов намеренно короткие: они уезжают в `callback_data`
кнопки, а Telegram обрезает её на 64 байтах. Вопрос со слишком длинными
идентификаторами не отправляется вовсе — лучше промолчать, чем прислать сломанные кнопки.

Требует колонки: `ALTER TABLE user_funnel_progress ADD COLUMN IF NOT EXISTS profile JSONB DEFAULT '{}'::jsonb;`
Пока её нет, прогресс сохраняется без профиля, а ответы живут до перезапуска.

## Вид воронки

При создании выбирается шаблон — лид-магнит, продающий урок, продажа услуги или
пустая воронка. Раньше он только раскладывал этапы и нигде не сохранялся, поэтому
отличить одну воронку от другой можно было лишь по названию. Теперь выбор остаётся
с воронкой в поле `type`.

Вид виден на карточке в списке воронок, и по нему же там фильтр — он появляется,
только когда видов больше одного. В галерее вид добавлен в тот же выпадающий
список, где отбирались файлы по конкретной воронке: пункты «Вид: Лид-магнит»
показывают файлы всех воронок этого вида.

У воронок, созданных до появления поля, вид пустой — в интерфейсе это «Без вида»,
и такие воронки тоже можно собрать отдельным пунктом фильтра. Проставить вид
задним числом нельзя: угадывать за владельца, что он имел в виду год назад,
хуже, чем честно показать пустоту.

## Отбор аудитории по анкете и источнику

Сегменты отвечают на вопрос «на каком шаге человек застрял»: получил не открыл,
прошёл не купил и ещё семь. Поверх сегмента можно наложить отбор по тому, что
человек о себе рассказал и откуда пришёл.

Условия берутся из вопросов воронки (`goal`, `level`, …) и из меток диплинков,
которые реально встречались. Внутри одного вопроса варианты складываются по
«или», между вопросами — по «и»: «цель = заказы И пришёл с VK». Отдельным
условием можно выбрать пришедших без метки.

Отбор работает и в ручной рассылке, и в запланированной, и в правилах
автосообщений. У запланированной он хранится вместе с кампанией, поэтому
отложенный запуск соберёт ту же аудиторию, что показал предпросмотр.

Человек, который на вопрос не ответил, под условие по этому вопросу не подходит:
отсутствие ответа — это не «любой ответ».

Пределы приходящего фильтра проверяются на сервере (`shared/audience.ts`):
не больше 10 ключей и 30 вариантов на ключ, значения обрезаются до 64 символов.
Список доступных условий отдаёт `GET /api/audience/filter-options`.

## Автопереход на следующий этап

Этап может уйти сам, без нажатия кнопки. В настройках перехода выбирается
задержка — «через 24 часа», «через 3 дня», — и следующий этап отправляется
по таймеру, если человек так и не нажал кнопку.

Кнопка при этом никуда не девается: нажал раньше — автопереход отменяется,
потому что переход на новый этап гасит все отложенные задачи предыдущего.
Условия отправки те же, что у напоминаний: человек всё ещё на этом этапе,
следующий этап ему ещё не приходил, бота он не заблокировал.

Задача живёт в той же очереди, что и напоминания (`reminderJobs`), поэтому
переживает перезапуск: `resumePendingReminders()` пересоздаёт таймер по
сохранённому сроку. У задач автоперехода `kind: "advance"`; у записей,
сделанных до этой версии, поля нет — они читаются как напоминания.

Выключатель «автонапоминания» в настройках на автопереход не влияет:
напоминание — это толчок к действию, а переход — сам шаг воронки. Тихих часов
у автоперехода тоже нет: он считает время от отправки предыдущего этапа, а не
по часам, поэтому урок может прийти ночью. Пока часовой пояс подписчика
неизвестен, выбирайте задержки кратными суткам — тогда следующий этап придёт
в то же время дня, что и предыдущий.

## Платная платформа

Открывается только из Telegram WebApp и только после оплаты. Прогресс по урокам
хранится в досье подписчика на сервере, поэтому переживает смену устройства и виден
в CRM — на нём же строятся сегменты вроде «купил, но не начал».

**У каждого урока свой адрес:**

```
/?funnel=<id>&stage=platform&lesson=<lessonId>
```

Это важнее удобства: на такую ссылку можно вести из напоминаний и ИИ-дожима, и
человек попадёт ровно на нужный урок, а не на общий список.

**Эфиры** хранятся в данных воронки и добавляются в админке, в разделе «Эфиры
платформы». До начала ученик видит анонс и ссылку на подключение, после — запись;
ссылка на подключение к прошедшему эфиру не отдаётся даже через API. Доступ к
эфиру можно ограничить старшим тарифом.

## Telegram Business: воронка в личной переписке

Бот умеет работать не только в своём чате, но и внутри личного аккаунта автора —
через Telegram Business. Для человека это обычная переписка с вами в личке, для
платформы — те же этапы, домашние задания и досье подписчика.

**Что нужно:** Telegram Premium у владельца аккаунта (Business-режим есть только
на нём) и бот, уже подключённый в админке.

**Как подключить:**

1. В Telegram: **Настройки → Telegram для бизнеса → Чат-боты**.
2. Указать username вашего бота.
3. Включить разрешение **отвечать на сообщения** (`can_reply`). Без него бот
   видит переписку, но ответить от вашего имени не может: студент не получит
   подтверждения, что домашка принята.

Сервер подписывается на `business_connection`, `business_message`,
`edited_business_message` и `deleted_business_messages` сам — и в production
(webhook), и локально (polling). Отдельных переменных окружения не требуется.

Когда связь установлена, в админ-чат приходит карточка с именем аккаунта, его ID
и правом на ответы. Уведомление придёт, только если в настройках указан
`Telegram Chat ID администратора` и включены уведомления.

**Что происходит с входящим сообщением:**

- сообщения самого владельца пропускаются — иначе ваш же ответ студенту
  засчитывался бы как сдача домашки, и на него отвечал бы ассистент;
- сообщение собеседника попадает в историю диалога с пометкой
  `[Telegram Business]` и обновляет активность подписчика;
- если у текущего этапа включено домашнее задание, текст уходит на первичный
  разбор модели, студенту прилетает ответ **из вашей личной переписки**, а вам —
  карточка с текстом работы, резюме ИИ и кнопками «Одобрить и открыть урок» /
  «На доработку»;
- если это не домашка, отвечает ИИ-ассистент воронки — при условии, что он
  включён в её настройках.

**Какая воронка выбирается.** Business-чат не несёт ничего, кроме собеседника:
ни диплинка, ни кнопки с идентификатором воронки. Поэтому берётся воронка того
же бота, в которой у человека есть прогресс (самый свежий по времени действия).
Если у бота всего одна активная воронка — она и подходит. Если воронок несколько,
а следов человека нет ни в одной, сообщение только записывается в историю: ни ДЗ,
ни ответа ассистента, ни добавления в подписчики — угадывать курс за студента
платформа не станет.

**Правки и удаления.** Исправленное сообщение попадает в историю с пометкой
`[Telegram Business, правка]`, удаление — строкой о числе удалённых сообщений.
Повторно такие обновления не разбираются: иначе одна и та же домашка уходила бы
куратору второй карточкой. Кто именно удалил сообщения, Telegram не сообщает.

**Ссылки «сдать ДЗ в личку».** В разделе «Настройки» есть поле *Telegram Username
автора / куратора* — из него страницы уроков строят ссылки, ведущие прямо в вашу
личную переписку.

**Ограничения:**

- разбирается только текст сообщения и подпись к медиа; файлы, фото и голосовые
  из личной переписки в историю не сохраняются и не расшифровываются;
- одобрение ДЗ и следующий урок отправляются **от бота**, а не из личной
  переписки, поэтому студент должен был хоть раз нажать боту `/start` — иначе
  Telegram не даст боту написать первым;
- Business-режим не заменяет `/start`: воронка начинается в чате с ботом, личная
  переписка — про сдачу домашних заданий и живое общение.

## ИИ-ассистент воронки

Когда подписчик пишет боту сам, ответить ему может ассистент на Claude. Включается
отдельно для каждой воронки в её настройках; по умолчанию выключен.

Что он видит: этап подписчика, какие уроки тот получил, открыл, досмотрел и завершил,
статус оплаты, а также структуру воронки и цены. Всё это подставляет сервер — модель
не додумывает факты о прогрессе и не называет своих цен.

У ассистента два независимых сценария, оба включаются в настройках воронки:

**Персонализация дожима.** Напоминания срабатывают ровно в точках отвала, но текст
в них один на всех. С включённой персонализацией ассистент переписывает его под
конкретного человека — с учётом того, что он открыл, где остановился и платил ли.
Кнопка, ссылка и условие отправки остаются из настроек напоминания: ИИ меняет только
формулировку. Если он недоступен, ответил пусто, слишком длинно или отказом —
уходит исходный текст шаблона. Напоминание не теряется никогда.

**Долгий дожим.** Ассистент сам решает, когда написать человеку, который замолчал:
раз в несколько дней, опираясь на его прогресс, ответы и прошлые касания. Каждое
решение — «написать / подождать / прекратить» — с причиной, которая пишется в лог.

Пределы проверяются в коде, а не в промпте, поэтому модель не может их обойти:
максимум касаний, минимальный разрыв между ними, срок всего дожима, тихие часы
(касание переносится на утро), не более 20 подписчиков за проход. Дожим
прекращается сам при оплате, блокировке бота, эскалации на оператора, исчерпании
касаний или окончании срока — и немедленно, если человек попросил не писать:
у ассистента для этого есть отдельный инструмент.

Это самая рискованная часть системы: месяц автосообщений — типичная причина, по
которой ботов массово жалуются и блокируют. Пределы здесь не украшение, а то, что
сохраняет бота живым.

**Ответы на сообщения.** Когда подписчик пишет боту сам. Что ассистенту при этом
разрешено, по нарастанию риска:

| Действие | По умолчанию | Ограничение |
| --- | --- | --- |
| Передать разговор человеку | всегда включено | подписчик помечается в «Аудитории»; метка снимается, когда оператор ответит |
| Повторно отправить этап | выключено | только этапы, которые подписчик уже получал |
| Дать ссылку на оплату | выключено | ссылку и цену подставляет сервер из настроек этапа |

Сообщения подписчика считаются недоверенными данными: ассистенту запрещено менять
по ним правила, выдавать скидки и открывать платные материалы. Сумму платежа он
назначить не может в принципе — ссылка ведёт на обычную подписанную страницу этапа.

Ключ вводится в разделе **«Настройки»** админки — там же, где токены ботов и ключи
Lava.top, и по тем же правилам: наружу отдаётся только маска, обратная отправка маски
не затирает сохранённое значение. Переменная окружения `DEEPSEEK_API_KEY` остаётся
запасным путём: если она задана, а в настройках пусто, ключ подхватывается из неё.

Модель — `deepseek-v4-flash` через Anthropic-совместимый эндпоинт DeepSeek
(`https://api.deepseek.com/anthropic`), поэтому в коде используется `@anthropic-ai/sdk`.

Расходы: DeepSeek кеширует общий префикс запроса автоматически, а структура воронки
одинакова для всех её подписчиков — поэтому по полной цене идёт только состояние
конкретного человека и переписка. Ориентир при off-peak тарифе: доли цента за ответ,
меньше цента за диалог из десяти сообщений. В часы пиковой нагрузки (01:00–04:00 и
06:00–10:00 UTC по будням) тариф вдвое выше. Число ответов одному подписчику в сутки
ограничивается в настройках воронки (по умолчанию 30).

Сменить провайдера можно в одном месте — константы `API_BASE_URL` и `MODEL`
в `server/services/assistant.ts`; тесты подменяют вызов модели через `createMessage`
и от провайдера не зависят.

## Railway

Конфигурация сервиса описывается в `.railway/railway.ts` (infrastructure-as-code).
В шаблоне этого файла нет — он свой у каждой установки:

```bash
npx railway config init    # создать .railway/railway.ts
npx railway config plan    # показать расхождения с Railway, ничего не меняя
npx railway config apply   # применить файл
```

`railway.toml` заводить не стоит: config-as-code объявлен устаревшим и работает
только до 2026-12-01. Файл требует Node 22+ (CLI выполняет его с
`--experimental-strip-types`), хотя само приложение собирается на Node 20. Билдер
указывать не нужно: Railway его не сохраняет, а `Dockerfile` в корне подхватывается
автоматически.

В конфигурации задайте healthcheck на `/api/health` и таймаут запуска 120 секунд:
полная загрузка истории из Supabase может занимать больше стандартных 30 секунд.
Трафик переключается после успешной проверки. Реплика должна быть одна — рассылки,
напоминания и очередь дожима живут в памяти процесса (см. «Ограничения
масштабирования»).

Минимальные переменные в Railway Variables для production:

- `NODE_ENV=production`
- `APP_URL=https://ваш-домен.up.railway.app`
- `ADMIN_EMAIL=ваш-email-в-Supabase-Auth`
- `SUPABASE_URL=https://ваш-project.supabase.co`
- `SUPABASE_SERVICE_KEY=...`
- `WEBAPP_SIGNING_SECRET=...` - любая уникальная строка длиной минимум 32 символа
- `VITE_SUPABASE_URL=https://ваш-project.supabase.co`
- `VITE_SUPABASE_ANON_KEY=...`

Если используется один env-токен Telegram-бота, добавьте `TELEGRAM_BOT_TOKEN`.
Если нужен вход по адресу без параметров (кнопка BotFather, `/sitelab`), добавьте `VITE_DEFAULT_FUNNEL_ID`.
Если нужно распознавание голосовых, добавьте любой из `XAI_API_KEY`, `GROQ_API_KEY`, `OPENAI_API_KEY`.
Если включены реальные платежи Lava.top, добавьте сразу обе переменные: `LAVA_API_KEY` и `LAVA_WEBHOOK_SECRET`.

Если сервер в Railway падает сразу после старта, в логах обычно будет строка `Invalid server configuration`.
Это означает, что одна из обязательных production-переменных отсутствует или всё ещё содержит placeholder.
